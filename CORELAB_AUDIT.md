# CoreLab Mini App — аудит ИИ-конфигуратора

Дата проверки: 2026-10-19. Основание: ТЗ «CoreLab — интеллектуальный конфигуратор ПК и ИИ-консультант по продажам», версия 1.0, предоставленное владельцем в задаче. Аудит ограничен чтением кода, документации, запуском существующих тестов и запросами без записи. Рабочий код, схема и данные не изменялись.

## Краткий вывод

Существуют каталог CoreLab, механизм допуска товаров, текущие предложения p1, локальный подбор полной сборки, диалог с ИИ и начальный экран согласования. Сквозного оформления заказа нет. Покупательский диалог и каталог Mini App пока работают как два отдельных экрана и через разные контуры авторизации. После нормализации значения сокета и перезапуска Mini App два проверенных расчёта стали успешными; требуется автоматическая проверка этого пути при обновлении сервиса. Дальнейшие задачи — устойчивая консультация и защищённое оформление внутри существующего Mini App.

Статусы ниже означают: **Реализовано** — код и успешная проверка; **Частично реализовано** — часть пути работает или есть только код/тест; **Не реализовано** — нет рабочего пути; **Требует проверки** — имеющихся свидетельств недостаточно; **Неактуально** — следует использовать уже существующий механизм либо требование противоречит принятой архитектуре.

## Архитектура и фактический поток

1. PostgreSQL хранит `Product`, `Category`, `Attribute`, `CategoryAttribute`, `ProductAttribute`, `SupplierOffer`, `ProductSourceLink`, статусы допуска и административный аудит: [models.py](corelab/backend/app/models.py). Миграции ведёт Alembic; API — FastAPI, административный интерфейс — React/Vite: [main.py](corelab/backend/app/main.py), [docker-compose.yml](corelab/docker-compose.yml), [main.tsx](corelab/frontend/src/main.tsx).
2. [mini_views.py](corelab/backend/app/mini_views.py) выдаёт каталог через защищённый потребительский API и внутренний `/api/v1/internal/builder/products`. `eligible()` требует включённую категорию, `validity_check=true`, `selection_enabled=true` и хотя бы одно известное техническое значение. Внутренний feed дополнительно требует текущую связанную цену KZT; читает базу в `REPEATABLE READ`. Это **не** означает полноту полей для конкретной сборки.
3. [mini_auth.py](corelab/backend/app/mini_auth.py) валидирует Telegram `initData`, выдаёт часовой bearer-токен, привязанный к организации. [catalog-client.mjs](corelab/mini-app/catalog-client.mjs) использует его без хранения каталога; [app.mjs](corelab/mini-app/app.mjs) показывает каталог на `/catalog-preview/`. Для браузерного предпросмотра используется административная сессия и CSRF. Фактический запуск в Telegram с настоящим ботом в этом аудите не подтверждён.
4. Покупательский диалог на `/mini-app/` обслуживает уже имеющийся сервис [preview-app.cjs](tools/preview-app.cjs), а интерфейс находится в [app.js](app/app.js), [index.html](app/index.html) и [mobile.css](app/mobile.css). Маршрут проксируется Vite; это действующий интерфейс, который надо развивать. Его `/api/chat` и `/api/pc-build` проверяют `Origin`, `Host`, JSON и размер тела, но **не используют** потребительский Telegram bearer-токен и не связывают диалог с организацией/пользователем. Внутренний feed сейчас жёстко выбирает организацию `1`.
5. [corelab-data.cjs](tools/corelab-data.cjs) преобразует свойства CoreLab и текущие предложения в кандидатов. Единственный локальный справочник для расчёта маршрутов — [supplier-delivery.json](config/supplier-delivery.json). [pc-builder.cjs](tools/pc-builder.cjs) в одном проходе проверяет часть совместимости, считает цену/максимальный срок перемещения, сравнивает сборки. [build-preferences.json](config/build-preferences.json) содержит редакционные приоритеты CPU/GPU, а не результаты тестов производительности.
6. [corelab-ai.cjs](tools/corelab-ai.cjs) вызывает Responses API с JSON-схемой, `store:false`; включает в контекст серверную `verifiedBuild`, если подбор удался. Профиль и история находятся в `Map` памяти процесса до часа бездействия, максимум 60 сообщений; перезапуск или открытие на другом устройстве теряет консультацию. Текст клиента передаётся модели без отдельного маскирования персональных данных.
7. [app.js](app/app.js) показывает сборку, цену и срок, ждёт явного согласия текстом, после него предлагает варианты оплаты. Выбор остаётся в памяти страницы; форма заказа, сущности сделки, менеджерского раздела и передачи в CRM нет. `?demo=1` показывает условные товары и суммы и позволяет пройти демонстрационный сценарий.

### Причина прежнего отказа и проверенное исправление

В живом каталоге единственный корпус-кандидат для Алматы — Deepcool CG330 3F: допустимая высота кулера 164 мм, поддержка радиаторов 240/360 мм. Единственный воздушный кулер-кандидат — Deepcool ASSASSIN IV VC VISION высотой 172 мм, поэтому он исключается. У пяти доступных СЖО сокет ранее был записан как `AMD AM5`, а у процессора — `AM5`; [buildPc()](tools/pc-builder.cjs) сравнивает строки дословно. В следующем запросе значение `AMD AM5` заменено на `AM5` у 14 СЖО, в том числе у всех пяти доступных в Алматы. После замены запущенный процесс Node продолжал отвечать 422: он держал старый модуль подборщика в памяти. Отдельный свежий процесс на том же feed уже выдавал две сборки; после `docker compose restart mini_app` их выдаёт и HTTP-сервис. Другие обозначения сокетов (`Intel LGA...`, `AMD AM4`) остаются неоднородными и требуют проверяемой нормализации без предположения о совместимости неизвестных значений.

## Риски и решения до реализации

- **P1: риск устаревшего процесса после изменения подборщика.** Файлы `tools/` смонтированы в контейнер, но Node загружает модуль при старте. Обновление файла/значений без перезапуска может оставить старые правила в памяти; после обновления нужен перезапуск сервиса и живой smoke. `builderAvailable=true` всё равно не доказывает наличие подходящей сборки для любого запроса.
- **P0: контур диалога не связан с Telegram-авторизацией.** `Origin`/`Host` не устанавливают личность клиента; существующий `/mini-app/session` следует использовать для запросов диалога, каталога и будущей заявки. Исключить жёсткую организацию `1` при клиентском доступе.
- **P0: персональные данные могут уйти в ИИ.** Пользователь пишет произвольный текст; имя вводится в клиентском сценарии. До выпуска защитить текст до модели, не хранить PII в истории и не считать чат формой заказа.
- **P1: между расчётом и согласием меняются цена/остаток.** Одного `expiresAt` недостаточно: нужна повторная серверная проверка версии сборки, цены, остатков и сроков при оформлении и смене оплаты.
- **P1: расхождение источников требований.** [PROJECT.md](PROJECT.md) отражает прежние решения: не спрашивать разрешение экрана, работать только с `priceLoan`, использовать локальное состояние сеанса. Новое ТЗ требует иного. Перед разработкой зафиксировать обновлённые бизнес-правила внутри существующего проекта, не меняя принципы единого каталога.
- **P1: покрытие данных и правил.** Категорийный допуск не заменяет проверку пары деталей; отсутствие данных должно давать «требуется проверка», а явный конфликт — «несовместимо». Не добавлять обязательные свойства, которые производитель не публикует; предусмотреть проверку менеджером.
- **P2: демонстрационный режим и устаревшие тесты.** Не допускать перехода демонстрационной сборки к реальному заказу. Обновить тесты под маршруты и действующие цели RAM/SSD до принятия следующих изменений.

## Границы подтверждения

Backend suite, настоящая Telegram-сессия, HTTPS, оплата, CRM и сквозной заказ в этой проверке не запускались и не подтверждены. Живые числа отражают локальную БД и снимок предложений на дату аудита. Содержание и сроки поставщика после последнего импорта отдельно не проверялись.
## Уточнение аудита: «Обязательно для конфигуратора»

Read-only срез действующей БД: 62 связи `category_attributes.required_for_selection=true` в 11 категориях, разрешённых для конфигуратора. У всех этих связей правило свойства имеет `level=required`. [revalidate_product()](corelab/backend/app/validity.py) проверяет заполненность товара; [componentFromAttributes()](tools/corelab-data.cjs) переносит лишь часть полей в подборщик; [buildPc()](tools/pc-builder.cjs) содержит отдельные сравнения. Поэтому флаг сейчас **работает как требование к заполненности**, но не гарантирует выполнения сравнения между компонентами. Матрица ниже отражает наличие именно фактического правила, а не просто наличие значения. «Частично» включает однонаправленные или неполные проверки; «нет» означает отсутствие использования обязательного поля в соответствующем правиле. Пары без второго товара относятся к соответствию задаче либо требуют отдельного правила качества, а не искусственного равенства двух характеристик.

Они разрешены конфигуратору, но отсутствуют в `CATEGORY_FACT` и адаптере сборщика. По решению владельца HDD добавляется **только по просьбе клиента**. Корпусные вентиляторы добавляются автоматически **в игровую сборку с корпусом без встроенных вентиляторов** либо **по просьбе клиента в свободные места корпуса**; число, размер и подключение должны быть проверены по данным выбранных корпуса и платы/контроллера. Если сведений о штатных вентиляторах или свободных местах не хватает, выводить «требуется проверка», не считать корпус укомплектованным по предположению. Изменение галочек либо действующих правил этим аудитом **не выполнялось**; для потенциально непроверяемых свойств сначала нужно согласовать правило или изменение требований на основании источника производителя.

## Уточнение источников, оценки и цены

Дополнение от 2026-10-19 после начала внедрения: действующая `selection_category` управляет допуском категории, а не её обязательным включением. Для второй настройки добавлена отдельная `Category.required_for_build` и переключатель в административном экране. Снимок настроек и его хеш теперь передаются в Mini App при каждом расчёте. Аудит 62 характеристик остаётся реестром недостающих сравнений: передача галочек сама по себе не подтверждает совместимость. История согласованных сборок пока не хранится на сервере; версия присутствует только в ответе расчёта. Для проверенного добавления вентиляторов необходимы подтверждённые свободные места корпуса и доступные разъёмы платы/контроллера, которых текущая БД не содержит.

Подтверждённая владельцем иерархия: каталог CoreLab для SKU, цены, наличия и складов; сайт производителя конкретной модели/ревизии для технических параметров; сопоставимые независимые испытания для производительности; авторитетные технические базы как дополнение; знания модели — только предварительная гипотеза. В качестве возможных источников испытаний названы TechPowerUp, Tom's Hardware, TechSpot/Hardware Unboxed, Gamers Nexus, Puget Systems, PassMark. Один синтетический рейтинг не заменяет оценку конкретной задачи. При конфликте данных неразрешённый параметр получает «требуется проверка».

В [models.py](corelab/backend/app/models.py) у `ProductAttribute` уже есть `source_url`, `source_kind`, `updated_at`; у `PropertyRule.definition` возможны `evidence_url` и `checked_on`. Это частичная база для происхождения технического свойства. `updated_at` не равен гарантированной дате получения доказательства; отдельного проверенного хранилища результатов независимых тестов и воспроизводимого журнала пяти критериев для конкретной рекомендованной сборки аудит не подтвердил. Текущие редакционные баллы [pc-builder.cjs](tools/pc-builder.cjs) не отвечают требованию шкалы 0–100 с доказуемыми основаниями. В будущем нужно хранить страницу, название источника, модель/ревизию, проверенный параметр, дату получения и версии использованных данных. Интернет-поиск при каждом расчёте не нужен.

Подтверждённое правило цены: текущий расчёт через `SupplierOffer.price` используется для рассрочки/кредита; при немедленной оплате позже будет бонусная цена, точное название и момент её появления владелец сообщит отдельно. До этого **все расчёты остаются по первой цене**; обещать бонусную сумму нельзя. При возвращении клиента на следующий календарный день или позже цену, наличие и срок получения каждого товара требуется проверить заново до повторного согласования. Имеющиеся поля `price_bonus`/`price_special` сами по себе не подтверждают, какое из них будет новой бонусной ценой.
