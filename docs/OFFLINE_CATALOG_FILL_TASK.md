# Наполнение карточек товаров без API

Статус: задание согласовано владельцем. Продолжение ранее начатого заполнения.

## Цель и границы

Заполнить все активные отсутствующие свойства товаров каталога CoreLab по проверяемым источникам, включая вложенные поля структурированных характеристик. Выполнять исследование через сайты и инструкции, запись — локальными скриптами в БД с проверкой и журналом. Не вызывать модели по API, платный загрузчик характеристик, внешние API обогащения или удалённую интеграцию p1. Не требуется отключать AI в клиентском приложении: запрет относится к этому заданию.

Начальный контекст — каталог Over, organization_id=1. Не переносить записи автоматически в другие организации. Наличие и цена определяют приоритет исследования, но их отсутствие не исключает карточку из дальнейшей проверки полноты. Не менять цены, остатки, связи источников, настройки организаций или правила совместимости.

## Перед началом

1. Прочитать [PROJECT.md](../PROJECT.md) и [.handoff/PROTOCOL.md](../.handoff/PROTOCOL.md), проверить очередь сообщений и свой курсор по протоколу.
2. Прочитать последние записи [плана проекта](../CORELAB_IMPLEMENTATION_PLAN.md), проверить существующие файлы `data/offline-core-cooling-properties-*`, чтобы не повторять выполненное и использовать найденные источники.
3. Сверить сохранённую очередь с текущей БД: файл является снимком, а не гарантией актуальности. Проверять ID, организацию, производителя, артикул, модель и ревизию.

## Очередь и порядок

Начать с [очереди после первого пакета](../exports/configurator-evidence-queue-2026-11-05-after-batch1.json): на момент снимка 55 карточек — 30 плат, 15 БП, 7 воздушных кулеров и 3 СЖО. Это только пробелы подключения у допущенных товаров с доступным предложением в Павлодаре, а не полный перечень незаполненных карточек.

Первый подтверждённый пакет уже записан: ASRock B650M-H/M.2+, ASRock H810M-X Gen5 WiFi, GamerStorm PQ650G и PQ1000G. Журнал БД: 47700. [Доказательства и прежние значения](../data/offline-core-cooling-properties-2026-11-05-connectivity-batch1.json), [проверка результата](../exports/connectivity-batch1-verification-2026-11-05.json).

Сначала закрывать подтверждаемые пробелы плат, БП и охлаждения, влияющие на совместимость. Для каждой открытой карточки проверять также остальные активные свойства её категории. Затем расширить очередь на остальные категории и недопущенные товары: процессоры, видеокарты, память, накопители, корпуса и далее остальной каталог. Не ограничиваться текущими 55 товарами или только обязательными для подбора полями.

Полноту определять по активной структуре категории и содержимому значений. Ноль в селекторе «без технических свойств» означает только отсутствие совершенно пустых карточек. Заполненный JSON или 100% верхнеуровневых обязательных полей не доказывают полноту вложенных параметров.

## Доказательства и нормализация

- Основные источники — официальные спецификации, инструкции и страницы точной модели. Разрешённые владельцем исключения описаны в PROJECT.md; не расширять их произвольно. Для AMD PPT допускаются ранее согласованные технические обзоры штатных лимитов.
- Для каждого изменённого свойства сохранять значение, единицу, URL, название источника, дату проверки и страницу/раздел инструкции. Отдельно отмечать интерпретацию схемы, если значение получено из распиновки, а не готовой таблицы.
- Не переносить сведения между похожими названиями, ревизиями, региональными комплектами или версиями PWM/ARGB без подтверждения идентичности. Для одинаковой модели другого цвета разрешён перенос общих характеристик с исправлением цвета; сначала подтвердить, что комплектация и конструкция совпадают.
- Не угадывать ток разъёма, число отдельных кабелей, контроллеры, схему питания, размеры, поддержку профилей памяти или CPU. Штекеры и кабели учитывать раздельно; ARGB 5V и RGB 12V не смешивать.
- Формулы резервного расчёта MTP/PPT из PROJECT.md не записывать как измеренные или опубликованные характеристики. Не придумывать оценки производительности по цене, названию или объёму памяти.
- Применять действующие нормализаторы и единицы проекта. Не создавать дубли свойств и не подменять неизвестное значение нулём, «нет» или неподтверждённым «не применимо».
- Если сведения не найдены или противоречат друг другу, оставить поле незаполненным и записать конкретную причину, проверенные источники и следующий способ проверки. Продолжить другие карточки.

## Запись и проверка каждого пакета

1. Подготовить файл доказательств с точными прежними значениями и перечнем изменений. Для иных категорий использовать соответствующий файл `offline-core-…-properties-*`.
2. Просмотреть изменения до записи. Сохранить существующие подтверждённые значения; исправлять их только при наличии доказательства ошибки с отдельным пояснением.
3. Записать пакет транзакционно с проверкой идентичности товара и актуальности исходных значений. Сохранить прежние значения и источники в журнале, чтобы изменения можно было восстановить. Использовать блокировку валидации проекта.
4. Перечитать БД, проверить нормализацию, отсутствие дублей и повторный запуск без новых изменений. Пересчитать полноту и допуск. Проверить, что другие свойства не потеряны.
5. Для свойств совместимости проверить фактическое поведение действующего валидатора на конкретных карточках. Отличать проверку одного подключения от полной совместимости сборки. Не ослаблять правила ради увеличения числа допущенных товаров.
6. Обновить очередь и план проекта: обработанные карточки, записанные свойства, оставшиеся пробелы, причины и следующий пакет. После записи продолжать следующий пакет, не запрашивая повторное разрешение на тот же объём работ.

Для уже подготовленных свойств подключения имеется [локальный скрипт применения](../corelab/tools/apply_offline_connectivity_evidence.py). Он ограничен двумя кодами свойств и organization_id=1; не применять его к другим данным без проверки и адаптации. Не запускать старые файлы пакетов вслепую.

## Критерии результата

- У каждого записанного значения есть проверяемый источник и журнал изменения.
- Все карточки согласованного каталога проверены по всем активным свойствам; отдельно учтены вложенные пробелы. Числа обработанных товаров и уникальных моделей не смешиваются.
- Остаток представлен конкретными товарами и свойствами с причинами. Проверенный, но неподтверждённый пробел не считается заполненным. Если такие пробелы остаются, итог обозначается как частичный, а не «всё заполнено».
- Платных вызовов и вызовов API-загрузчиков характеристик в рамках задания — 0. Обычное чтение официальных страниц и локальная работа с БД разрешены.
- После заполнения вернуться к разнообразию подбора, ограниченным проверкам офис/игры/творчество, общему и независимому аудиту. Напомнить владельцу о завершении сделки: отправка предложения через WhatsApp, Telegram и почту со сроком действия цены. Это следующий этап, не разрешение сейчас отправлять сообщения клиентам.
