# CoreLab — техническое задание и поэтапный план
Версия: 1.8 · 2026-10-18

Рабочая копия исходного ТЗ v1.1 из пакета заказчика. Дополнение «СВОЙСТВА»
от 2026-10-17 находится в `docs/STAGE_05_PROPERTIES.md` и является частью этого ТЗ.
В вопросах структуры категории и блокировки ИИ действует дополнение; остальные
требования v1.1 сохраняются. Решение владельца от 2026-10-17: проверки и требования
Используется ограниченный набор выбранных владельцем полей GMC; остальные требования GMC не проверяются. Изменения ниже — план, не отчёт о реализации.

Уточнение владельца: универсальные внутренние правила характеристик, четыре уровня
обязательности, условия и требования каталога описаны в
`docs/UNIVERSAL_PROPERTY_RULES.md`.

Уточнение владельца от 2026-10-18: в Mini App передаются только товары со статусом
«Доступен для Конфигуратора» — обязательные характеристики товара проверены, категория
участвует в конфигураторе, а товар не исключён вручную.

## 0. Режим работы агента
- Работать строго по одному этапу. Не начинать следующий без явного подтверждения заказчика.
- До изменений прочитать `CORELAB_SPEC.md`, `AGENT_RULES.md`, `PROJECT_STATUS.md`, `HANDOFF.md`, проверить git status/diff и реальный код.
- На каждом этапе: реализация → автотесты → ручная smoke-проверка → отчёт → обновление MD → остановка.
- Никаких заявлений «тесты прошли» без фактического запуска; записывать команды, exit code, количество пройденных/упавших тестов.
- Не менять существующий Mini App или исходную БД p1.over...; доступ к источнику только read-only.
- Все новые файлы в `corelab/`. Не сохранять секреты в репозитории.
- Любое несовпадение с существующим кодом или отсутствие доступов — сообщить и остановиться, не придумывать.

## 1. Назначение
Каталог сайта — единственный владелец товарных записей и источник товаров для Mini App. CoreLab служит закрытой админ-системой для работы с каталогом сайта, связанными предложениями источников, нормализованными характеристиками и ценами; ссылки на товары сайта сохраняют их стабильные идентификаторы. Mini App получает товары из каталога сайта через версионированный API и не создаёт, не хранит и не редактирует собственный каталог товаров. Визуальный стиль админ-системы — цвета, шрифты и компоненты существующего Mini App, после анализа исходников.

## 2. Стек (утвердить после анализа)
Предпочтительно Python/FastAPI, PostgreSQL/SQLAlchemy/Alembic, React/TypeScript/Tailwind, Docker Compose; фоновый worker с единственным планировщиком; REST JSON OpenAPI. Если Mini App диктует иной совместимый стек — согласовать на этапе 1.

## 3. Безопасность
- Вся UI-функциональность в `/admin`; `/admin/login`, защищённые API. Слева разделы «Каталог», «Свойства», «Источники», «Журнал» и «Настройки».
- Начальную учётную запись создавать из `ADMIN_USERNAME` и `ADMIN_PASSWORD` локального окружения, хранить Argon2id-хеш, никогда не хранить plaintext в коде/логах; при нелокальном запуске требовать смены пароля.
- HTTP-only cookie, CSRF-защита для cookie-auth, rate limit входа, проверка ролей, безопасные настройки cookie.
- Отдельная авторизация будущего Mini App/API; минимальные права на чтение.

## 4. Модель данных
- users; categories (source_id, parent_id, name, `selection_category BOOLEAN NOT NULL DEFAULT FALSE`); products (source_id, SKU, manufacturer_article, name, price, currency, status, `validity_check BOOLEAN NULL`, `selection_enabled BOOLEAN NOT NULL DEFAULT TRUE`, image_url/image_path); product_categories для множественной принадлежности; attributes (unique code, label, type, unit, normalization); category_attributes (required_for_selection); product_attributes (unique product_id + attribute_id для одиночного значения, typed value, source URL, source kind, updated_at); jobs; job_items; audit_logs; import_logs; validation_reasons.
- Реальную схему уточнить после обследования источника. Системные поля и пустое изображение не считаются техническими свойствами.
- Товарные записи каталога сайта остаются каноническими; локальные ссылки и нормализованные данные CoreLab должны сохранять стабильный идентификатор товара сайта. Mini App не хранит отдельную мастер-копию каталога.
- Нормализовать сокеты (LGA 1700→LGA1700), десятичные разделители с учётом типа, размерности (12 cm→120 mm). Не объединять семантически разные свойства. Многозначные свойства моделировать явно.
- Сохранять источник/время и историю изменений. Не удалять ручные данные при импорте.

## 5. Каталог и карточка
- Дерево всех категорий; возле каждой категории inline-переключатель `selection_category`, независимый от родителя, автосохранение и индикатор «валидных/всего».
- Каталог списком: `[checkbox] [expand] название товара ... цена справа`; раскрытие всех характеристик одной строки/всех строк текущей страницы; переход в карточку; поиск название/SKU/артикул; сортировка название/цена; серверная пагинация; фильтры validity_check.
- Карточка показывает свойства, цену, источник, причины невалидности. Карандаш → input/типизированный редактор → галочка сохранить/крестик отменить. После сохранения транзакционно обновить БД и проверить товар.
- Категории: через админку настраивать обязательные характеристики `required_for_selection`. Изменения инициируют переоценку затронутых товаров.
- Массовое редактирование выбранных товаров: выбор атрибута/значения, предпросмотр количества, подтверждение перезаписи, нормализация, журнал, повторная проверка.

## 6. ИИ-загрузка характеристик
- Повторно использовать ранее написанный алгоритм Mini App, предварительно найти и изучить код.
- Только официальные сайты производителей, точное совпадение производителя и модели, источник URL и дата. Нельзя придумывать характеристики, использовать маркетплейсы и сторонние магазины. При неоднозначности — «требует проверки», без записи сомнительных значений.
- Строгое правило: загрузка (индивидуальная и по категории) разрешена только товару с НУЛЁМ заполненных технических свойств. При хотя бы одном заполненном свойстве — пропустить. Частично заполненные товары дополняются только вручную/массовым редактированием.
- В одной фоновой задаче сначала собрать весь доступный набор, проверить модель, нормализовать, затем сохранить атомарно. Повторно проверить условие «ноль свойств» непосредственно перед записью для исключения гонок.
- Характеристики, влияющие на совместимость: корпус — max GPU length, CPU cooler height, PSU length, form factors; БП — form factor, length, power, connectors; GPU — dimensions, power connectors; CPU — socket, cores/threads, TDP, integrated graphics; motherboard — socket, RAM, form factor; и др. Отделять размеры товара, упаковки и ограничения совместимости.
- Очередь, ограничение параллелизма, статус/прогресс, безопасные повторы, лог ошибок; не запускать массовую загрузку всего каталога без отдельного согласования.

## 7. validity_check
- `true`: все обязательные свойства категории корректны; `false`: отсутствуют/неверны; `null`: товар не входит ни в одну категорию с `selection_category=true`.
- Каждый товар может быть связан не более чем с одной категорией. Это ограничение обеспечивается базой данных; импорт новой категории заменяет предыдущую связь товара. Проверка применяет требования единственной категории.
- Worker проверяет применимые товары каждые 15 минут. Немедленно — после правки товара, массовой правки, ИИ-загрузки, изменения флагов категорий/обязательных атрибутов. Сохранять причины false.
- `selection_enabled` позволяет исключить валидный товар вручную. validity_check — не проверка совместимости двух конкретных товаров: это отдельная логика Mini App.

## 8. Журнал
`/admin/logs`: операции импорта, AI, ручных/массовых правок, проверок и ошибок. Дата, тип, товар/категория, статус, причина, ссылка. Фильтры даты/типа/статуса/товара; прогресс фоновых работ: всего/готово/пропущено/ошибки. История переживает перезапуск.

## 9. API
- `GET /api/v1/categories`, `/api/v1/products`, `/api/v1/products/{id}`, `/api/v1/selection/products` с пагинацией, фильтрацией и нормализованными типизированными значениями и единицами.
- В API для Mini App включать только товары со статусом «Доступен для Конфигуратора»: `validity_check=true`, `selection_enabled=true` и хотя бы одна связанная категория имеет `selection_category=true`. Товар с отсутствующими или некорректными обязательными характеристиками, не участвующей категорией либо ручным исключением в приложение не передавать.
- Административные операции только в защищённом `/api/v1/admin/...`. OpenAPI/Swagger. Mini App на этом проекте не менять.

## 10. Этапы с обязательным тестированием

### Этап 2 — Каркас и вход
Создать `corelab/`, миграции, БД, backend/frontend, защищённый `/admin`, логин и меню «Каталог»/«Журнал». **Автотесты:** pytest auth success/failure, 401/403, password hash, CSRF, logout; frontend routing smoke; миграции up/down; контейнер healthchecks. STOP.

Дерево, список, поиск, сортировка, пагинация, expand all, `selection_category` inline. **Автотесты:** API фильтры/сортировка/пагинация; frontend component/e2e (Playwright) раскрытие, переходы, toggle, сохранение после reload, независимость родителей и детей. STOP.

Attributes, category_attributes, нормализация, изображение как поле, редактор требований категории. Дополнительно: CRUD структуры, блокировка свойств для ИИ, предложение структуры по 2–5 официальным моделям и действующая кнопка «Проверить структуру свойств». **Автотесты:** уникальность кодов, эквивалентность единиц/сокетов, числовые локали, разделение несовместимых семантик, сохранение required_for_selection; CRUD/блокировки, исследование 2–5 моделей и сброс проверки после правки. Дополнение владельца от 2026-10-17: для пустой категории администратор запускает исследование кнопкой в интерфейсе структуры. Сервер через ИИ изучает 2–5 точных моделей, формирует свойства категории, проверяет цитируемые ссылки и сохраняет результат вместе с источниками и записью в журнале. Сгенерированные свойства остаются рекомендациями каталога; ИИ не назначает обязательность для GMC или подбора ПК. API-ключ задаётся в разделе «Настройки», хранится зашифрованным и не возвращается в интерфейс или журнал. Формирование запрещено, если структура категории уже заполнена. Это не заменяет этап 8: автоматическое заполнение пустых карточек товаров остаётся отдельной задачей.
Дополнение владельца от 2026-10-24: приоритет имеет официальный сайт производителя точной модели. Когда нужной характеристики там нет, разрешены только страницы Белого Ветра (`shop.kz`), DNS (`dns-shop.kz`) и Технодома (`technodom.kz`) для той же точной модели. ИИ и загрузчик сохраняют URL и отдельный тип источника для каждого значения; сомнительные значения пропускают.

### Этап 6 — Карточка и редактирование
Типизированный редактор, карандаш/галочка/крестик, источники значений, добавление атрибутов. **Автотесты:** API create/update, ошибки валидации, cancel без записи, UI edit/save/reload, права доступа, триггер перепроверки. STOP.

### Этап 8 — ИИ-загрузка с разрешённых источников
Дополнение этапа 5 обязательно: worker проверяет актуальную внутреннюю структуру, блокировки свойств и соответствие товара категории; при несоответствии или неопределённости пропускает товар без записи значений и сохраняет причину в журнале. Повторяет проверки перед атомарной записью. Правило нуля заполненных технических свойств сохраняется.
Адаптировать существующий Mini App-код, атомарная загрузка только пустых товаров, background jobs. **Автотесты:** подтверждение официального или разрешённого резервного источника, точное совпадение модели, отсутствие данных, запрет прочих магазинов, ноль/одно свойство, конкурирующее ручное изменение, транзакция, retry, логирование. Сначала тестовая выборка, без массового запуска. STOP.

### Этап 9 — Массовое редактирование
Выбор, preview, подтверждение, типизированная запись, журнал. **Автотесты:** выборка 20 товаров, mixed filled/empty, rollback на ошибке по определённой политике, повторная проверка, e2e подтверждения. STOP.

### Этап 10 — Журнал
Включить сохранённые с этапов 5 и 8 события проверки структуры, изменения и блокировки свойств, пропуски из-за несоответствия категории. Хранение этих событий не откладывать до появления отдельной вкладки.
Отдельная вкладка, фильтры, прогресс, persistence. **Автотесты:** события от каждой операции, фильтрация, пагинация, прогресс, восстановление после перезапуска, отсутствие секретов в логах. STOP.

### Этап 10А — Вкладка «Свойства»
Добавить отдельный раздел `/admin/properties`: список свойств каталога и фактически записанные значения выбранного свойства с числом товаров для каждого значения. Администратор создаёт значение любого типа даже без назначенных товаров, меняет записанное значение у всех связанных товаров или подтверждённо удаляет значение из карточек. Для свойств всех типов администратор отмечает два или более значения и выбирает одно из отмеченных как итоговое, видит число затронутых товаров и явно подтверждает атомарное объединение. Сервер повторно сверяет количества, сохраняет источник каждого изменённого значения, пересчитывает допуск товаров и пишет аудит с автором. Новые значения «Графический процессор» нормализуются при ИИ-загрузке и ручной/массовой записи: префикс `NVIDIA` перед `GeForce` и `AMD` перед `Radeon` убирается. Список категорий и переход в существующий редактор остаются доступны по `/admin/properties/categories`. Доступ и API защищены администраторской сессией; запись требует CSRF. **Автотесты:** список и значения, CRUD, нормализация, предпросмотр/подтверждение, отказ при устаревших количествах, атомарная запись, сохранность источников, аудит и доступ. STOP.

### Этап 11 — API Mini App
Интегрировать Mini App с каталогом сайта через версионированный read-only API, typed JSON, авторизацию и OpenAPI. Каталог сайта остаётся единственным владельцем товарных записей: Mini App показывает полученные данные и передаёт ссылки на стабильные идентификаторы сайта, без собственной копии/редактирования товаров. В Mini App передавать исключительно товары со статусом «Доступен для Конфигуратора»: `validity_check=true` (все обязательные характеристики проверены), `selection_enabled=true` (нет ручного исключения) и хотя бы одна связанная категория имеет `selection_category=true`. Товары с любым другим статусом не должны присутствовать ни в выдаче каталога для приложения, ни в подборе. Цены и актуальные предложения должны соответствовать последнему успешно сохранённому снимку каталога. **Автотесты:** contract tests OpenAPI, выборка только товаров со статусом «Доступен для Конфигуратора» и их цен сайта, отсутствие товаров с `validity_check=false/null`, `selection_enabled=false` или без участвующей категории, pagination, 401/403, отсутствие независимой записи/изменения товара в Mini App, устойчивость JSON schema. STOP.

### Этап 12 — Интеграционная приёмка
Прогнать все тесты (pytest, frontend unit, Playwright, API contracts, migration smoke), smoke Docker Compose, резервная копия/восстановление тестовой БД, сверка полноты каталога, отчёт о покрытии и ограничениях. **Критерий:** ноль критических ошибок; известные некритические — документировать и согласовать. STOP.

### Этап 13 — Связь товаров источников с товарами каталога
Спроектировать и реализовать отдельные связи между записями источников/предложений и каноническими товарами CoreLab. Автоматически связывать только однозначные совпадения по идентификаторам и правилам конкретного источника; неоднозначные случаи направлять в очередь ручной проверки. В интерфейсе дать возможность подтвердить, заменить и снять связь с записью в журнале. Не сливать записи источников и не менять исходные данные. Для over-shop действует точное совпадение `article + manufacturer`; подключение этого источника начинать только после появления `skuOver` в sitemap инфоблока 23 и отдельного разрешения владельца. **Автотесты:** точное/частичное/неоднозначное совпадение, отсутствие обоих идентификаторов, дубликаты, ручное подтверждение и снятие связи, идемпотентность, запрет изменения исходной записи, аудит. ### Этап 14 — Автоматическое обновление снимка каталога

Предусмотреть ручной запуск, включение/приостановку расписания, единственный scheduler, блокировку параллельных запусков, прогресс, безопасные повторы и журнал ошибок. Обновления выполняются независимо от клиентского диалога; диалог использует последний успешно сохранённый снимок. Автоматический доступ к живому источнику и расписание включать только после проверки доступа и отдельного разрешения владельца. **Автотесты:** расписание через подменённые часы, повторный запуск, конкурентный запуск, частичный сбой и откат, новые/изменённые/исчезнувшие предложения, сохранность ручных свойств, неизменность источника, восстановление после перезапуска. ## 11. Единый тестовый протокол каждого этапа
- Тесты должны быть детерминированными и не обращаться к живой исходной БД или сайтам в CI. Использовать фикстуры, моки, тестовую PostgreSQL и тестовый API.
