# Единая настройка ИИ

В `/admin/settings` главный администратор выбирает OpenAI, Kimi напрямую
или OpenRouter, сохраняет API-ключ и ID модели. Последний сохранённый или явно
выбранный провайдер используется для исследования структуры категорий,
загрузки характеристик товаров и диалога Mini App этой организации.
Ключи разных провайдеров хранятся отдельно в зашифрованном виде в CoreLab.
Ключ не передаётся браузеру или процессу Mini App.

Для OpenRouter введите ключ OpenRouter и точный ID модели из его каталога,
например `moonshotai/kimi-k2.5`. Суффикс `:free` используйте только если он
есть у доступной модели в актуальном каталоге; бесплатные модели и лимиты
меняются. Кнопка «Проверить подключение» проверяет ключ и наличие модели,
не выполняя платный запрос модели. Исследование характеристик через OpenRouter
вызывает веб-поиск, который может тарифицироваться отдельно.

Mini App обращается к внутреннему маршруту CoreLab с подписью запроса;
CoreLab выбирает ключ своей организации и сам вызывает провайдера. Локальный
`.secrets/corelab-ai.json` больше не читается и не подключён к контейнеру.
После смены настройки новые сообщения диалога используют новый провайдер.

При исследовании товара проверяются точная модель, официальный домен
производителя и подтверждённые характеристики. Для структуры категории Kimi
использует страницы производителей; если в категории указан один производитель,
достаточно двух разных моделей этого бренда. OpenAI и OpenRouter принимают
подтверждённые поиском страницы без требования официального домена. OpenRouter возвращает URL
поисковой системы в аннотациях; URL из сгенерированного текста не считаются
доказательством. При отсутствии таких ссылок исследование прекращается.

Документация API:
- https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request
- https://openrouter.ai/docs/guides/features/server-tools/web-search
- https://openrouter.ai/docs/api/api-reference/api-keys/get-current-key

## Пробный запуск категории 273 (МФУ лазерные), 2026-10-21

Активный прямой провайдер: Kimi, модель `kimi-k2.6`. Структура категории была
пустой. Реальные задания 24, 25 и 26 завершились без записи свойств:

- №24: генерация не завершилась за исходные 5 минут ожидания.
- №25: ответ получен, но свойство «Режимы качества печати» не ссылалось на
  модель из списка исследованных; первоначальная проверка отклонила весь ответ.
- №26: после изменения обработки неподтверждённых свойств ни одно предложение
  Kimi не содержало совпадающего названия исследованной модели.

Ожидание генерации увеличено до 10 минут. Теперь свойства без подтверждающей
модели пропускаются и перечисляются в результате задания; если таких свойств
все, задание завершается ошибкой. Проверка базы после первых трёх запусков:
`property_rules` для категории 273 оставалась пустой, записи исследования не было.
Сырой ответ провайдера не сохраняется, поэтому причину несовпадения названий
моделей по этим трём заданиям определить нельзя.

Дополнение 2026-10-21: ограниченная диагностика названий и URL моделей,
сообщённых для отклонённых свойств, добавлена в результат неудачного задания
и интерфейс. Backend-тесты: 17/17, сборка frontend успешна. Следующий реальный
запуск №27 завершился успешно: Kimi предложил 12 свойств по пяти моделям Canon
и HP, пропусков не было, проверка структуры вернула `success`. Свойство
`product_code` («Код продукта») дублировало поле артикула карточки и было
архивировано штатным API с аудитом. В категории осталось 11 активных
рекомендательных свойств; структура по-прежнему имеет статус `success`.
Canon-источники ведут на страницы настроек руководств серий, где отдельные
пункты могут различаться по модели; перед использованием этих правил для
автоматической загрузки карточек нужна предметная проверка точных моделей.
