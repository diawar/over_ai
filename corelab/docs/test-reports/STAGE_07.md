# Этап 7 — проверка допуска к подбору

Реализован 2026-10-17. Независимое ревью запрошено отдельно.

`validity_check` вычисляется транзакционно: null, если нет непосредственно назначенной
категории с включённым подбором; false при ошибках обязательных для подбора свойств;
true при выполнении требований. Родительская категория не включает дочерние автоматически.
Объединяются требования всех назначенных категорий. Используется существующий флаг
`required_for_selection`; обязательность заполнения карточки и выбранные поля GMC
остаются отдельной проверкой. Отсутствие рекомендуемых свойств не блокирует подбор.
Если структура выбранной категории отсутствует, допуск закрыт. Настроенная структура
без обязательных для подбора свойств проходит проверку; администратор задаёт обязательность.

Причины сохраняются в validation_reasons, изменения статуса/причин — в audit_logs.
Повторная проверка того же результата не дублирует аудит. Неизвестная применимость
обязательного свойства и противоречивые требования блокируют допуск с объяснением.
`selection_enabled` независимо разрешает или запрещает участие; ручное исключение
не подменяет результат проверки свойств.

События: сохранение значения, создание/изменение/архивирование правила, установка
шаблона, изменение флага категории, импорт связей товара с категориями. Все выполняются
в одной транзакции с пересчётом. Новые массовые операции и AI-загрузчик должны вызвать
тот же сервис внутри своей транзакции (эти операции относятся к следующим этапам).

Worker принадлежит жизненному циклу FastAPI, запускает проход при старте, затем через
900 секунд после завершения предыдущего. Обрабатывает по 100 товаров в транзакции;
ошибку пишет в серверный лог и повторяет проход в следующий интервал. Общая advisory
блокировка сериализует пересчёты и изменения. Категорийные операции синхронные;
время выполнения на больших выбранных категориях требует отдельного нагрузочного теста.

В карточке: «Участие в подборе», ручной переключатель и кнопка «Проверить для подбора».
После изменения категории обновляются статусы каталога и счётчики дерева.
Полная проверка сохранённых правил остаётся отдельной кнопкой.

Проверено: backend 48 тестов; frontend 16 тестов; Playwright 2 сценария;
TypeScript/Vite production build. Backend покрывает true/false/null, сохранение значений,
объединение категорий, конфликт ограничений, неизвестную применимость, ручное исключение,
идемпотентность аудита, реальный проход worker и искусственные часы/восстановление после ошибки.
Тестовая БД изолирована от рабочего каталога. Локальные контейнеры обновлены.
Загрузка значений с сайтов производителей — этап 8, здесь не реализована.
